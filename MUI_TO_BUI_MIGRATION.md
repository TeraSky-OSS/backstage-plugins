# MUI → Backstage UI (BUI) Migration

This document is the internal playbook for migrating this repo's first-party frontend plugins off Material-UI v4 (`@material-ui/core`/`icons`/`lab`) and onto [Backstage UI](https://ui.backstage.io) (`@backstage/ui`, "BUI"). It exists so that ~19 plugins are migrated against **one** convention instead of each plugin author inventing their own.

## Goal and non-goals

**Goal:** zero direct `@material-ui/*` imports in the source of our own plugins, replaced with `@backstage/ui` (BUI) equivalents and one shared styling/icon convention.

**Explicitly NOT a goal (at least not yet):**
- Zero MUI in the built bundle. `@backstage/core-components` (`InfoCard`, `Table`, `Page`, `Header`, `Status*`, etc. — used ~620 times across our plugins) is itself still built on MUI v4 upstream (tracked in [backstage/backstage#31467](https://github.com/backstage/backstage/issues/31467), ~13% complete as of writing). MUI will keep loading transitively via `core-components` regardless of what we do here.
- Replacing any `@backstage/core-components` import with a hand-rolled BUI equivalent. Reimplementing Backstage's own standard components would fork our look-and-feel away from every other plugin in a consumer's app and would need re-doing once upstream finishes its own migration. Wait for upstream instead.
- `packages/app/src/theme.ts`'s MUI `styleOverrides` block (targets Backstage's own still-MUI `SidebarSubmenu` — see that file's migration notes when reached).

**Before hand-rolling any BUI replacement, check whether `@backstage/core-components` already has a wrapper.** Confirmed during the pilot (`devpod-plugin`): `@backstage/core-components` exports `CopyTextButton` (already BUI-based internally, with a nicer built-in "copied" tooltip than a hand-rolled `ButtonIcon` + `navigator.clipboard`) and `SimpleStepper`/`SimpleStepperStep` (still MUI-based internally, but satisfies our "no direct `@material-ui/*` import in our own source" rule — this is exactly the fix for the `spectrocloud` `Stepper` case, see the exception list). Grep `node_modules/@backstage/core-components/dist/index.d.ts` for a relevant name before writing new BUI composition from scratch.

## Styling decision ladder

Every `makeStyles`/`createStyles` block must be classified into exactly **one** tier below. If you find yourself inventing a fifth approach, stop and raise it instead of merging it.

**Tier 0 — Delete.** Pure layout/spacing (`margin`, `padding`, `display: flex`, `gap`, alignment) → replace with BUI layout primitive props (`Flex`, `Grid`, `Box` — `gap`, `p`/`px`/`py`, `align`, `direction`, etc.). This should be the default assumption for most blocks; ask "why isn't this Tier 0?" before reaching for anything else.

**Tier 1 — Semantic token substitution.** Anything derived from `theme.palette.*` or `theme.spacing(n)` → a BUI CSS custom property (see table below). This is also the mechanism that removes every `theme.palette.type === 'dark' ? X : Y` branch outright — one semantic var replaces the whole ternary, because BUI's custom properties flip automatically with the active theme.

**Tier 2 — Co-located CSS Module** (`Component.module.css`), only for genuinely component-specific static CSS with no primitive equivalent (e.g. a graph/canvas container, an editor's fixed sizing). **Confirmed working** (spiked against `devpod-plugin` on 2026-09-06): `backstage-cli package build` compiles `*.module.css` via rollup + postcss-modules into a `*.module.css.esm.js` file that injects the scoped CSS at runtime via a bundled `style-inject` helper (the same mechanism `@backstage/ui` itself uses internally) and exports a class-name map (`import styles from './Component.module.css'; styles.foo`). No separate `.css` asset is emitted, so there's no consumer-side bundler/extraction concern. Tier 2 is safe to use.

**Tier 3 — Inline `style` prop.** Only for values computed at runtime (graph node coordinates, a color derived from API/entity data, a measured width). Never for static values — if it's static, it belongs in Tier 0 or 1.

**`useTheme`** (from `@material-ui/core`) is banned outright, with one documented exception class: a third-party library that requires a JS boolean/string for light-vs-dark (not CSS), e.g. Monaco's `vs-dark`/`vs-light` theme name in `plugins/template-builder/src/components/YAMLEditor/YAMLEditor.tsx`. Such cases go on the [exception list](#documented-mui-exception-list) rather than being silently reintroduced ad hoc elsewhere.

**⚠️ BUI's `Responsive<T>` breakpoint object is mobile-first — the opposite direction from MUI's `theme.breakpoints.down('sm')` idiom.** Confirmed by reading the generated CSS (`node_modules/@backstage/ui/dist/css/styles.css`): a responsive value like `direction={{ initial: 'row', sm: 'column' }}` compiles to `.bui-fd-row` (applies always) plus `.sm\:bui-fd-column` wrapped in `@media (min-width: 768px)` — i.e. **column applies at 768px and *wider*, not narrower**. Writing `{ initial: 'row', sm: 'column' }` to mean "row on desktop, column on small screens" (the natural MUI translation) does the **opposite**: it forces column layout on every normal desktop viewport. This exact bug shipped in `api-docs-module-crd`'s `CrdDefinitionWidget` (the Kind/Group/Version header rendered as three full-width stacked headings instead of a compact row, and a Flex-wrapped `Button` stretched to a full-width bar because the parent had collapsed to a single-column stack) — caught by the user visually, not by lint or tests, since nothing in the automated checks renders the component at a real viewport size. **Do not use a responsive breakpoint object to replicate a MUI `down()` collapse-to-column pattern.** If you actually need a hard breakpoint switch, invert the mental model (`sm` = "at this width and up"); but for the common "wrap onto a new line on narrow screens" case, prefer a static `direction="row"` plus `style={{ flexWrap: 'wrap' }}` — that's what actually replicates the old MUI behavior and needs no breakpoint math at all.

**⚠️ Don't render your own `<Header>`/`<ContentHeader>` from `@backstage/core-components` on a top-level `PageBlueprint` page — the new-frontend-system's `core-page-layout` (`@backstage/plugin-app`'s `PageLayout`, wired automatically by `packages/app`) already wraps every page's content in BUI's `PluginHeader`, sourced from that page's `PageBlueprint.make({ params: { title, icon } })`.** Rendering a plugin's own `Header` banner on top of that produces a visibly duplicated title (confirmed on both `frontend-extensions-explorer` and `educates` — screenshotted by the user as "the old plugin header"). Fix: delete the page's own `<Header>` (and generally the `<ContentHeader>` too, since it's typically vestigial once `Header` is gone); keep `<Page>`/`<Content>` for the theme id and padding. Any header-level custom actions (icon links, buttons) that used to live inside `<Header>` should become a `PluginHeaderActionBlueprint.make({ params: { loader: () => Promise<JSX.Element> } })` extension registered alongside the page in `createFrontendPlugin({ extensions: [...] })` — this is the same mechanism Backstage's own `techdocs`/`app-visualizer` use for their header icons, and it renders in the correct toolbar slot automatically (see `educates`'s `EducatesHeaderActions.tsx` + `alpha.tsx` for a worked example). **This only applies to standalone top-level pages** (`PageBlueprint`); `entity-content`/`entity-card` tabs render inside the catalog entity page's own layout and never had this problem (repo-wide grep found exactly 5 files using `<Header` from `core-components`: `educates`, `frontend-extensions-explorer` — both fixed — plus 3 files in the not-yet-migrated `spectrocloud` plugin, which will need the same fix when its turn comes).

**⚠️ BUI `Text`'s `title-large` variant is sized for a page-level `<h1>`, not a section heading inside a card/drawer/panel.** Reusing it for a smaller in-context heading (e.g. a drawer's "Kubernetes Manifest" title, or a sub-label like "Actions") renders it wildly oversized relative to its container — shipped in `kubernetes-resources`'s resource-detail drawer (both `KubernetesResourceGraph.tsx` and `KubernetesResourcesPage.tsx`), caught by the user from a screenshot, not by lint/tests/build. Pick the variant by the heading's actual visual weight in context: `title-small`/`title-x-small` for panel/drawer/card section headings, `title-large`/`title-medium` reserved for actual page titles. Fixed by downgrading to `title-small` (drawer/section titles) and `title-x-small` (sub-labels like "Actions"), and moving the drawer's close button into a `Flex justify="between"` row alongside the title instead of floating separately above it.

**⚠️ Without a brand-token override, BUI components render with BUI's own generic default palette — not the app's active custom theme — even though `@backstage/core-components` (still-MUI) correctly follows it.** Caught by the user comparing two adjacent `InfoCard`s on the same entity page: `devpod-plugin`'s still-MUI card correctly showed the TeraSky dark theme's paper color, while `kyverno-policy-reports`'s migrated BUI `Card` showed a visibly different (BUI-default) background — "they don't have the same look at all including colors," reproduced only after switching the app to a TeraSky theme (BUI's own defaults happened to look closer to Backstage's stock theme, masking the gap until then). Root cause: `@backstage/ui/css/styles.css` defines its `--bui-*` custom properties inside `@layer tokens`, scoped to `[data-theme-mode='light']`/`[data-theme-mode='dark']` (set on `document.body` by Backstage's theme system based on the active theme's `variant`) — but nothing in `packages/app` ever populated those properties with the TeraSky palette from `theme.ts`; BUI was rendering its own shipped defaults the entire time. Fixed by adding `packages/app/src/bui-theme-tokens.css` (imported in `index.tsx` right after `@backstage/ui/css/styles.css`), which re-declares the subset of `--bui-*` tokens that are both (a) genuinely brand-specific in `theme.ts` and (b) actually referenced by migrated plugins' CSS (backgrounds, accent, and the four status colors — see the palette table below), under the same `[data-theme-mode='...']` selectors, **without** wrapping them in `@layer`. Per the CSS cascade spec, an un-layered rule always beats a layered one regardless of specificity or source order, so this file overrides BUI's own tokens no matter where it's imported relative to `styles.css`. Verified via `getComputedStyle` on `document.body` for both `data-theme-mode="light"` and `"dark"` — every overridden token now matches `theme.ts`'s `teraskyLightTheme`/`teraskyDarkTheme` values exactly, and a same-entity-page `InfoCard`-vs-`Card` background comparison in both modes now matches (`rgb(255,255,255)` light, `rgb(30,30,30)` dark, only remaining difference is a `border-radius` (4px MUI vs 8px BUI), an accepted cosmetic difference between the two libraries' default card corners, not a bug). **This file is a Phase-4-sized concern landed early, out of tier order** — it was pulled forward because it silently affected every already-migrated plugin's visual output, not just the plugin whose turn it would have been in Phase 4. Text/divider tokens (`--bui-fg-primary`/`-secondary`/`--bui-border-1`) were deliberately left un-overridden since `theme.ts` doesn't customize MUI's `text.*`/`divider` palette fields either (confirmed via `@backstage/theme`'s palette source) — BUI's own near-black/near-white defaults already track that.

## Palette / token substitution table

**The left column below is verified** — extracted directly from `node_modules/@backstage/ui/dist/css/styles.css` (not guessed), so these exact variable names exist regardless of the Terasky brand palette. **The *values* are now Terasky-branded**, via `packages/app/src/bui-theme-tokens.css` (see the ⚠️ callout above) — landed early (out of tier order) once the generic-BUI-palette bug was found, rather than waiting for the full Phase 4 `theme.ts`/`Sidebar.tsx` migration. Full variable list available by grepping `styles.css` for `--bui-` if a case below isn't covered.

**Important — deprecated tokens exist and the linter catches them.** The shared `@backstage/cli/config/eslint-factory` config includes a `@backstage/no-deprecated-bui-tokens` rule that warns whenever a deprecated `--bui-*` custom property appears in a JS/TS string (see `node_modules/@backstage/eslint-plugin/docs/rules/no-deprecated-bui-tokens.md` for the full migration table). **Always run `yarn lint` after using a raw `var(--bui-*)` string** — don't assume a name is current just because it appears in `styles.css` (deprecated tokens are kept for backward compatibility, so they still resolve, they just shouldn't be used in new code). The table below already reflects the *non-deprecated* replacements; the ones we initially got wrong (`--bui-fg-danger`, `--bui-bg-danger`, `--bui-fg-success`, `--bui-bg-success`, `--bui-fg-info`, `--bui-bg-info`) are noted so nobody reintroduces them from an old commit or a web search.

| MUI v4 (`theme.palette.*` / `theme.spacing`) | BUI CSS custom property | Notes |
|---|---|---|
| `theme.palette.text.primary` | `var(--bui-fg-primary)` | |
| `theme.palette.text.secondary` | `var(--bui-fg-secondary)` | |
| `theme.palette.background.default` | `var(--bui-bg-app)` | |
| `theme.palette.background.paper` | `var(--bui-bg-neutral-1)` (or `-2`/`-3`/`-4` for nested surfaces) | BUI has 4 neutral surface levels, not MUI's flat default/paper split — pick by nesting depth |
| `theme.palette.divider` | `var(--bui-border-1)` (or `-2` for a stronger divider) | |

| `theme.palette.error.main` | `var(--bui-fg-negative)` (text) / `var(--bui-negative-bg-subdued)` (background) | **not** `--bui-fg-danger`/`--bui-bg-danger` — those are deprecated |

## Icon strategy

**Corrected after inspecting the installed package (`@backstage/ui@0.17.1`, checked directly in `node_modules`):** contrary to what published BUI docs/blog posts suggest, **there is no exported `Icon` component and no Lucide-based registry in this version.** `node_modules/@backstage/ui/dist/index.d.ts` exports no `Icon`/icon-registry symbol at all — every BUI component that takes an icon (`Alert`, `Badge`, `Button`, `ButtonIcon`, `PluginHeader`, etc.) takes a raw `icon?: ReactElement` / `iconStart?`/`iconEnd?` prop. `@backstage/ui`'s own `package.json` lists `@remixicon/react": ">=4.6.0 <4.9.0"` as a dependency (not `lucide-react`), i.e. **RemixIcon**, not Lucide. So icon components are plain React elements the plugin author supplies — there's no name-based registry to look up.

**Convention:** each plugin gets its own small `src/icons.ts` barrel that re-exports **only the icons that plugin uses**, under a **semantic name** (`CopyIcon`, not `FileCopyIcon` — the migration is the cheap moment to fix MUI-name leakage), backed by `@remixicon/react`'s `Ri<Name><Style>` components (style suffix is usually `Line` for outline, some also have `Fill`). Components import from `../icons`, never directly from `@remixicon/react`. This keeps a single swap point per plugin if the underlying icon set changes later.

**Dependency note:** `@remixicon/react` is only a *transitive* dependency via `@backstage/ui` today. Because these are published packages installed into arbitrary consumer apps, any plugin that imports `@remixicon/react` components directly (via its `icons.ts` barrel) must add `@remixicon/react` as an **explicit** dependency in its own `package.json`, pinned to the same range `@backstage/ui` expects (`>=4.6.0 <4.9.0` as of `@backstage/ui@0.17.1` — re-check this range when bumping `@backstage/ui`). Relying on hoisting without declaring it is a phantom-dependency bug waiting to happen for a published package.

**Do not create a shared published icon package.** All 19 plugins are independently versioned and published (`@terasky/backstage-plugin-*`); a shared icon package would force a coordinated version bump across all of them for what is fundamentally a static lookup table. The cost isn't worth it — duplicate the barrel per plugin.

## Per-plugin Definition of Done

A plugin is **Migrated** only when all of the following are true:

1. Zero imports of `@material-ui/core`, `@material-ui/icons/*`, `@material-ui/lab` anywhere in `src/`, except entries on the [exception list](#documented-mui-exception-list).
2. Zero `makeStyles`, `createStyles`, and zero MUI `useTheme`, except exceptions (each exception carries a `// BUI-EXCEPTION:` comment pointing at its row in the exception list).
3. Zero `theme.palette.type === 'dark'` (or equivalent) branches.
4. `@material-ui/core`, `@material-ui/icons`, `@material-ui/lab` removed from that plugin's `package.json` `dependencies` — **unless** a still-required third-party dependency lists one of them as a peer dependency (confirmed case: `terraform-scaffolder` keeps `@material-ui/core`/`@material-ui/icons` because `@rjsf/material-ui`, used via `withTheme(MuiTheme)` to theme its dynamic form, requires them at runtime — check `node_modules/<pkg>/package.json` `peerDependencies` before assuming a leftover MUI dep is dead). Such cases still satisfy rule 1 (no *direct* import in our own `src/`) and must be noted in the [exception list](#documented-mui-exception-list).
5. `@backstage/ui` added to that plugin's `package.json` `dependencies` (not `peerDependencies` — decided for this repo: simpler for consumers, accepted tradeoff of possible duplicate-copy edge cases), at the version `packages/app` uses.
6. Visual parity verified in both light and dark themes **by actually looking at the rendered page in a browser** (a real viewport, not just `jsdom` test assertions that elements exist — `jest`/`@testing-library` cannot catch a wrong layout direction, a stretched button, or a broken responsive breakpoint; see the `CrdDefinitionWidget` incident above, which passed lint, 23/23 tests, and a clean build while visibly broken).
7. `yarn workspace <pkg> lint && test && build` all green; built `dist/` spot-checked once (catches CSS-Modules-in-published-package issues if Tier 2 is used).
8. That plugin's `.eslintrc.js` has `no-restricted-imports` enabled banning `@material-ui/core`, `@material-ui/icons/*`, `@material-ui/lab`.
9. That plugin's install docs (`site/docs/plugins/<name>/frontend/install.md` where present) note the `@backstage/ui/css/styles.css` requirement for consumers who haven't already got it (most will, via `packages/app`, but this is a published package installed into arbitrary Backstage apps).
